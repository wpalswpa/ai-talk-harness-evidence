# 003. Windows에서 Codex가 프롬프트의 첫 줄만 받았다

2026-10-11. 운영 기록을 다시 읽다가 발견했다. Codex 참여자에게 보낸 여러 줄 프롬프트가 Windows에서 첫 줄만 도착했다. 프롬프트를 명령줄 인자 대신 stdin으로 보내도록 고쳤다.

## 무엇이 잘못됐나

2026-09-22 수집 실행 대화 2개에 Codex 출력 9건(발언 8, 결과물 1)이 실행 배너째 저장돼 있다. 001에서 다룬 사용 한도 실패 기록이다. 배너에는 Codex가 실제로 받은 프롬프트가 `user` 절로 찍힌다.

| 비교 | 값 |
|---|---|
| 배너 `user` 절(Codex가 받은 것) | 9건 모두 과제 한 줄(42자, 43자) |
| 같은 시각 Codex 호출의 입력 길이 기록(하네스가 보낸 것) | 8회 288~3,958자(초안 1회 288자, 의논 7회 1,641~3,958자) |

결과물 1건은 같은 시각의 호출이 없어 길이 비교에서 뺐다. 하네스가 보낸 프롬프트는 과제, 역할, 지금까지의 의논, 말하기 규칙을 줄을 바꿔 이어 붙인 것이다. Codex는 그중 첫 줄인 과제만 받았다. 다른 참여자의 의논 내용을 보지 못한 채 답한 셈이다.

정상 응답에서는 파서가 배너를 버리므로 `user` 절이 남지 않는다. 그래서 잘림이 전체 Codex 호출 37회 중 몇 번 일어났는지는 세지 못했다. 이 PC에서 Codex를 부른 경로가 모두 같았으므로 여러 줄 프롬프트는 매번 잘렸을 것으로 본다(추론).

2026-09-24에는 Codex 호출 10회가 모두 실패했다. 입력 길이는 8,422~9,284자였고 모두 0.11초 안에 끝났다. 성공한 호출의 최대 입력은 7,673자였다. 아래 탐침에서 8,000자 이상은 cmd.exe가 "명령줄이 너무 깁니다"로 거부했다. 9/24 실패의 오류 본문은 대화 기록에서 빠져 있어, 원인이 길이 제한이라는 것은 추론이다.

## 원인

`Member.ask()`는 `codex`를 PATH에서 찾아 절대경로로 실행한다. Windows에서 npm 전역 설치의 `codex`는 `codex.CMD` 래퍼다. `.CMD`는 cmd.exe가 실행하고, 래퍼는 받은 인자를 `%*`로 node에 넘긴다. 이때 cmd.exe가 명령줄을 다시 해석한다.

- 인자 안의 줄바꿈에서 명령이 끝난다. 첫 줄만 남는다.
- `%이름%`이 환경변수로 바뀐다.
- 따옴표 수가 홀수인 뒤의 `&`는 다음 명령으로 실행된다.
- 명령줄 길이 제한(8,191자)을 넘으면 실행되지 않는다.

Python의 `subprocess`는 인자를 C 런타임 규칙에 맞게 따옴표로 감싸지만 cmd.exe의 규칙은 다르다. 직접 실행하는 `.exe`에서는 문제가 없고 `.CMD`를 거칠 때만 생긴다. Claude 참여자는 `claude.exe`라 이 경로를 지나지 않는다.

탐침(npm `codex.cmd`와 같은 래퍼, 대상만 받은 인자를 기록하는 스크립트로 바꿈)에서 확인한 것:

| 보낸 프롬프트 | 도착한 것 |
|---|---|
| 서버 프롬프트 모양 20줄 507자 | 첫 줄 27자 |
| `값=%변수% 끝` | 변수 값으로 바뀜 |
| 홀수 따옴표 뒤 `& echo ... > 파일` | 파일이 생김(명령 실행) |
| 7,000자 한 줄 | 그대로 |
| 8,000자 한 줄 | 실행 실패 |

## 고친 것

- `Codex.build()`는 프롬프트 자리에 `-`를 둔다. Codex 0.155.1의 `exec` 도움말에 "인자로 주지 않거나 `-`를 쓰면 지시를 stdin에서 읽는다"고 적혀 있다.
- `Member.ask()`는 `prompt_via_stdin`이 켜진 참여자(Codex)에게 stdin을 파이프로 열고, 프롬프트를 UTF-8 바이트로 쓴 뒤 닫는다(`communicate(input=...)`). 나머지 CLI 참여자는 전처럼 stdin을 닫은 채(`DEVNULL`) 실행한다. 어느 쪽도 서버의 stdin을 물려받지 않는다.
- 하위 프로세스를 바이트 모드로 연다. 텍스트 모드로 쓰면 Windows에서 stdin에 쓴 `\n`이 `\r\n`으로 바뀐다(실행 확인). 출력은 전과 같이 UTF-8로 읽고 줄바꿈을 `\n`으로 맞춘다.
- `-`는 이미지 인자(`-i`)보다 앞에 둔다. `-i`가 값을 여러 개 받는 옵션이면 뒤에 둔 `-`가 이미지 경로로 읽힐 수 있다. 실제로 그런지는 확인하지 않았고, 위치로 피했다.

버린 대안:

| 대안 | 버린 이유 |
|---|---|
| cmd.exe용으로 `^`·`%` 이스케이프 | 줄바꿈은 cmd.exe 인자로 넘길 방법이 없고, 길이 제한도 남는다 |
| 래퍼를 건너뛰고 node로 `codex.js`를 직접 실행 | npm 설치 구조에 묶인다. 다른 설치 방식에서 깨진다 |
| 프롬프트를 파일로 쓰고 경로를 넘김 | `exec`에 프롬프트 파일 옵션을 확인하지 못했다. stdin은 도움말에 적힌 경로다 |

되돌릴 조건: Codex가 `-`를 stdin 표지로 읽지 않게 바뀌면 다시 본다.

## 검사

| 검사 | 무엇을 보나 | 옛 동작(인자 전달)에서 |
|---|---|---|
| `test_codex_build_puts_dash_not_prompt_on_command_line` | 명령줄에 프롬프트가 없고 `-`가 이미지 인자 앞에 있다 | 실패 |
| `test_prompt_arrives_byte_exact_on_stdin` 6개(모든 OS) | 가짜 CLI를 직접 실행. 20줄, `%`, `&`, 홀수 따옴표, `^ \| < >`, 9,000자 프롬프트의 UTF-8 바이트 길이와 SHA-256이 같다 | 통과(직접 실행은 인자로도 온전하다) |
| `test_prompt_survives_windows_cmd_shim` 6개(Windows) | 같은 프롬프트를 npm 래퍼 모양 `.CMD`를 거쳐 보낸다. 바이트 일치, 주입 파일 없음 | 6개 모두 실패 |
| `test_runtime_stdin_carries_prompt_then_closes_even_if_server_stdin_stays_open` | 서버 stdin이 열려 있어도 CLI가 프롬프트만 읽고 끝난다 | 실패(stdin에 아무것도 오지 않는다) |

직접 실행 시험이 옛 동작에서도 통과하는 것은 의도한 대조다. 같은 프롬프트가 직접 실행에서는 온전하고 래퍼를 거칠 때만 깨진다는 것이 원인을 가른다.

## 한계

- 실제 Codex로 둘째 줄 이후의 지시를 따르는지는 아직 확인하지 않았다. 구독 사용량이 들어 사람이 한 번 실행해 볼 일로 남겼다.
- Gemini CLI 참여자 클래스도 `gemini.CMD`를 거쳐 `-p` 인자로 프롬프트를 넘긴다. 이 저장소의 참여자 목록에는 쓰이지 않아 고치지 않았다.
- 이미 쌓인 9/22~9/28 기록의 Codex 발언은 잘린 프롬프트에 답한 것이다. 기록은 고치지 않았다.
